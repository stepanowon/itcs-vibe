## 1. 개요

### 1.1 배경

사람들은 하루의 감정과 경험을 기록하고 싶어 하지만, 일기는 본질적으로 매우 사적인 콘텐츠다. 기존의 SNS나 메모 앱은 공유 지향적이거나 보안이 취약해 "나만 볼 수 있는 안전한 기록 공간"에 대한 니즈를 충족하지 못한다.

본 프로젝트는 **개인 인증 기반의 프라이빗 일기 서비스**를 제공한다. 사용자는 자신만의 계정으로 로그인하여 일기를 작성하고, 그날의 날씨·기분·태그와 함께 기록을 남긴다. 나아가 축적된 기록을 다양한 조건으로 필터링·조회하여 자신의 감정 흐름을 되돌아볼 수 있다.

또한 본 프로젝트는 **3-tier 아키텍처(프론트엔드 / 백엔드 / 데이터베이스)** 와 **SOLID·Clean Architecture 원칙**, **자체 JWT 인증** 등을 학습·실습하기 위한 교육용 레퍼런스 구현체의 성격을 겸한다.

### 1.2 목표

- 회원 가입 및 자체 JWT 인증(Access/Refresh Token) 기반의 로그인 기능을 제공한다.
- 로그인한 사용자가 제목·본문·날씨·기분·태그를 포함한 일기를 작성·관리할 수 있게 한다.
- 날씨·기분·태그 기준의 필터링 및 조회 기능을 제공한다.
- 사용자 정보 조회(작성 일기 수 포함) 및 패스워드 변경 기능을 제공한다.
- 3-tier 구조와 Clean Architecture를 준수하는 유지보수 가능한 코드베이스를 구축한다.

### 1.3 비목표 (Non-Goals)

- 일기의 **공유·공개·소셜 기능**(팔로우, 좋아요, 댓글 등)은 제공하지 않는다.
- **소셜 로그인(OAuth, Google/Kakao 등)** 은 이번 범위에서 제외한다. (인증은 자체 JWT로만 구성)
- **이미지/파일 첨부, 음성 일기** 등 텍스트 외 미디어 기능은 제외한다.
- **AI 감정 분석/추천** 등 지능형 기능은 제외한다.
- **모바일 네이티브 앱**은 제외하며, 웹(반응형)만 대상으로 한다.
- **다국어(i18n)** 및 **관리자(Admin) 백오피스**는 제외한다.

## 2. 문제 정의

### 2.1 사용자 문제

- **프라이버시 불안**: 기존 메모/일기 앱은 누구나 접근하기 쉽거나 클라우드 동기화 과정에서 사생활 노출 우려가 있다. 사용자는 "인증된 나만 볼 수 있다"는 확신을 원한다.
- **단순 기록의 한계**: 단순 텍스트 저장만으로는 그날의 맥락(날씨, 기분)이 남지 않아 나중에 되돌아볼 때 감정의 흐름을 파악하기 어렵다.
- **검색·회고의 어려움**: 기록이 쌓일수록 원하는 일기를 찾기 어렵다. "비 오던 날", "우울했던 날", "#여행" 같은 조건으로 빠르게 찾고 싶다.
- **자기 활동 파악 부재**: 내가 얼마나 꾸준히 기록했는지(작성 일기 수 등)를 한눈에 확인할 수단이 없다.

## 3. 목표 및 성공 지표

### 3.1 핵심 목표

1. 안전한 자체 인증(회원가입/로그인/토큰 갱신)으로 **본인만 접근 가능한** 일기 공간을 보장한다.
2. **풍부한 메타데이터(날씨·기분·태그)** 를 가진 일기 CRUD를 제공한다.
3. **필터/조회** 를 통해 축적된 기록을 쉽게 다시 찾을 수 있게 한다.
4. 사용자가 자신의 계정과 활동(일기 수, 비밀번호)을 관리할 수 있게 한다.

### 3.2 성공 지표

| 구분 | 지표 | 목표 |
| --- | --- | --- |
| 기능 완성도 | 요구된 핵심 기능(인증/작성/필터/사용자관리) 동작 | 100% 정상 동작 |
| 보안 | 타인의 일기에 접근 가능한 케이스 | 0건 |
| 성능 | 일기 목록 조회 응답 시간 (P95) | < 500ms |
| 인증 | Access Token 만료 시 Refresh를 통한 자동 재발급 성공률 | 100% |
| 코드 품질 | 계층(Controller/Service/Repository) 간 의존성 규칙 위반 | 0건 |

### 3.3 실패 조건

- 인증되지 않은 요청으로 타인의 일기를 조회/수정/삭제할 수 있다.
- 로그인 없이 일기 작성 API가 동작한다.
- 비밀번호가 평문(암호화되지 않은 상태)으로 저장된다.
- Refresh Token 만료/폐기 후에도 Access Token이 계속 재발급된다.
- 필터 조건(날씨/기분/태그)이 결과에 정확히 반영되지 않는다.

## 4. 사용자 시나리오

### 4.1 페르소나

**페르소나 A — 지민 (28세, 직장인)**
- 하루를 마무리하며 감정을 정리하고 싶어 하는 사용자.
- 남에게 보이고 싶지 않은 솔직한 감정을 안전하게 기록하길 원한다.
- 나중에 "힘들었던 날"만 모아보며 스스로를 돌아보고 싶어 한다.

**페르소나 B — 하준 (23세, 대학생/취준생)**
- 꾸준한 기록 습관을 만들고 싶어 한다.
- 태그(#공부, #운동, #면접)로 기록을 분류하고, 자신이 얼마나 기록했는지 수치로 확인하며 동기부여를 얻고 싶어 한다.

### 4.2 사용자 스토리

- **US-1**: 사용자로서, 나는 이메일과 사용자명으로 **회원 가입**하여 나만의 계정을 만들고 싶다.
- **US-2**: 사용자로서, 나는 **로그인**하여 인증된 상태로만 서비스를 이용하고 싶다.
- **US-3**: 사용자로서, 나는 제목·본문·**날씨·기분·태그**를 담아 **일기를 작성**하고 싶다.
- **US-4**: 사용자로서, 나는 내가 쓴 일기를 **목록으로 조회**하고 상세 내용을 보고 싶다.
- **US-5**: 사용자로서, 나는 내 일기를 **수정·삭제**하고 싶다.
- **US-6**: 사용자로서, 나는 **날씨/기분/태그로 필터링**하여 원하는 일기를 빠르게 찾고 싶다.
- **US-7**: 사용자로서, 나는 **내 정보와 작성한 일기 수**를 조회하고 싶다.
- **US-8**: 사용자로서, 나는 **비밀번호를 변경**하여 계정 보안을 유지하고 싶다.
- **US-9**: 사용자로서, 나는 로그인이 오래 유지되어(토큰 자동 갱신) **자주 다시 로그인하지 않아도** 되게 하고 싶다.

### 5.3 우선순위 기준

- **P0 (필수)**: 없으면 제품이 성립하지 않는 핵심 기능. MVP 필수. (인증, 일기 CRUD, 필터, 소유권 검증, 사용자 조회/비번 변경)
- **P1 (중요)**: 완성도를 높이지만 MVP 이후로 미룰 수 있는 기능. (로그아웃/토큰 폐기, 태그 자동완성 등)
- **P2 (선택)**: 있으면 좋은 개선 사항. (정렬 옵션 확장, 통계 시각화 등)

우선순위 판단 기준: ① 보안·데이터 무결성 → ② 핵심 사용자 가치(작성/조회) → ③ 편의성.

## 6. 사용자 흐름 (User Flow)

```
[방문] 
  └─> 회원가입 ──> 로그인 화면
        │
[로그인] ─(email/username + password)─> 인증 성공 ──> Access/Refresh Token 발급 ──> 홈(일기 목록)
        │                                   └─ 실패 ──> 오류 메시지
        │
[홈: 내 일기 목록]
  ├─> [일기 작성] ─> 제목/본문/날씨/기분/태그 입력 ─> 저장 ─> 목록 갱신
  ├─> [일기 선택] ─> 상세 보기 ─> [수정] / [삭제]
  ├─> [필터] ─> 날씨/기분/태그 선택 ─> 조건에 맞는 목록 조회
  └─> [내 정보]
         ├─> 프로필 + 작성 일기 수 조회
         └─> 비밀번호 변경

[토큰 만료 시]
  Access Token 만료 ─> Refresh Token으로 자동 재발급 ─> 요청 재시도
  Refresh Token 만료 ─> 로그인 화면으로 이동
```

## 7. 범위

### 7.1 In Scope

- 회원 가입 / 로그인 / 로그아웃
- 자체 JWT 인증 (Access 12h / Refresh 7d), 토큰 재발급
- 일기 CRUD (제목·본문·날씨·기분·태그)
- 날씨·기분·태그 필터링 및 목록/상세 조회
- 사용자 프로필 조회, 작성 일기 수 조회, 비밀번호 변경
- 3-tier 구조: **Vue(최신) + TanStack Query + 전역 상태관리** 프론트엔드 / **Node + Express(JS)** 백엔드 / **Supabase PostgreSQL** DB

### 7.2 Out of Scope

- 소셜 로그인(OAuth), 이메일 인증/비밀번호 재설정 메일
- 일기 공유·공개·소셜 상호작용
- 이미지/파일/음성 등 미디어 첨부
- AI 감정 분석·추천
- 모바일 네이티브 앱, 다국어, 관리자 백오피스
- Supabase Auth/Storage 등 PostgreSQL 외 Supabase 부가 기능

## 8. 엣지 케이스 및 예외 처리

| 구분 | 케이스 | 처리 방안 |
| --- | --- | --- |
| 회원가입 | 이미 존재하는 email/username | 409 Conflict, 중복 안내 메시지 |
| 회원가입 | 비밀번호 정책 미달(길이/복잡도) | 400 Bad Request, 검증 메시지 |
| 로그인 | 존재하지 않는 계정 / 비밀번호 불일치 | 401 Unauthorized (계정/비번 구분 없이 동일 메시지로 정보 노출 방지) |
| 인증 | Access Token 만료 | 401 반환 → 클라이언트가 Refresh로 재발급 후 재시도 |
| 인증 | Refresh Token 만료/폐기/위조 | 401, 재로그인 유도 |
| 인증 | 토큰 없이 보호된 API 접근 | 401 Unauthorized |
| 권한 | 타인의 일기 조회/수정/삭제 시도 | 403 Forbidden (또는 존재 은폐를 위해 404) |
| 일기 | 존재하지 않는 일기 ID | 404 Not Found |
| 일기 | 필수 필드(제목/본문) 누락 | 400 Bad Request |
| 일기 | 정의되지 않은 날씨/기분 값 | 400 Bad Request (허용값 검증) |
| 일기 | 태그 개수/길이 초과 | 400, 제한 안내 (예: 태그 최대 10개, 각 20자) |
| 필터 | 조건에 맞는 결과 0건 | 200 OK + 빈 목록 |
| 필터 | 잘못된 필터 파라미터 | 400 Bad Request |
| 사용자 | 비밀번호 변경 시 현재 비밀번호 불일치 | 400/401, 변경 거부 |
| 공통 | 예상치 못한 서버 오류 | 500 Internal Server Error, 표준 에러 포맷 |
| 공통 | 과도한 요청(로그인 시도 등) | (P1) Rate limiting 고려 |
