## 1. 개요

### 1.1 배경

임직원 20명 내외의 소규모 중소기업은 별도의 근태관리 시스템 없이 수기 또는 엑셀로 출퇴근과 연차를 관리하는 경우가 많다. 이런 방식은 기록 누락, 연차 승인 이력 관리 부재, 월별 현황 집계의 어려움 등 여러 문제를 일으킨다. 이를 해결하기 위해 소규모 사업장에 적합한 경량 근태관리 웹 애플리케이션을 구축한다.

### 1.2 목표

- 직원의 출근/퇴근 기록을 시스템으로 관리한다.
- 연차 신청과 승인/반려 프로세스를 전산화한다.
- 관리자와 직원이 각자 권한 범위 내에서 월별 근태 현황을 조회할 수 있게 한다.
- 회원가입, 로그인, 역할 기반 접근 제어(RBAC)를 통해 안전하게 서비스를 이용하게 한다.

### 1.3 비목표

- 급여 계산, 4대 보험, 세무 연동 등 급여/인사 정산 기능은 다루지 않는다.
- 근무 스케줄(교대 근무, 시프트) 관리 기능은 다루지 않는다.
- 생체 인식, GPS 기반 위치 인증 등 고급 출퇴근 인증 방식은 다루지 않는다.
- 모바일 네이티브 앱(iOS/Android)은 다루지 않는다. 웹 기반으로만 제공한다.
- 다국어(i18n) 지원은 다루지 않는다.
- 비밀번호 재설정(이메일 발송 기반 등)은 다루지 않는다. 비밀번호 분실 시 관리자를 통한 수동 재설정은 향후(P2) 검토한다.

## 2. 문제 정의

### 2.1 사용자 문제

- 직원 입장에서는 출퇴근 기록을 별도로 남길 방법이 없어 근태 증빙이 어렵고, 연차 신청 시 서면/구두로 요청해야 하는 번거로움이 있다.
- 관리자 입장에서는 직원별 출퇴근 기록과 연차 사용 내역을 취합하기 어렵고, 연차 승인 이력이 명확히 남지 않아 분쟁 시 근거 자료가 부족하다.
- 회사 전체적으로 월별 근태 현황을 한눈에 파악할 수 있는 수단이 없다.

## 3. 목표 및 성공 지표

### 3.1 핵심목표

- 직원이 로그인 후 1분 이내에 출근/퇴근 체크를 완료할 수 있다.
- 연차 신청부터 승인/반려까지의 전 과정이 시스템 내에서 추적 가능하다.
- 관리자가 전체 직원의 월별 근태 현황을 하나의 화면에서 조회할 수 있다.

### 3.2 성공 지표

- 전체 직원(20명 내외)의 일별 출근 체크인 기록률 90% 이상.
- 연차 신청 건의 승인/반려 처리 소요 시간 평균 24시간 이내.
- 관리자의 월별 현황 조회 기능 주 1회 이상 사용.

### 3.3 실패 조건

- 출퇴근 기록이 누락되거나 중복 기록되어 신뢰할 수 없는 데이터가 쌓이는 경우.
- 연차 승인/반려 이력이 누가, 언제 처리했는지 추적되지 않는 경우.
- 관리자 계정이 최초 가입자 외에는 생성될 수 없어 운영이 막히는 경우.

## 4. 사용자 시나리오

### 4.1 페르소나

- **일반 직원(김사원)**: 매일 출퇴근 시각을 기록하고, 필요 시 연차를 신청하며, 본인의 근태 현황을 확인하고 싶어 한다.
- **관리자(박팀장)**: 직원들의 연차 신청을 검토해 승인/반려하고, 전체 직원의 월별 근태 현황을 파악해 인사 관리에 활용하고 싶어 한다.

### 4.2 사용자 스토리

각 스토리는 완료 조건(Acceptance Criteria)을 포함한다.

- 신규 입사자로서, 이메일/이름/사번/입사일/비밀번호를 입력해 회원가입하고 싶다.
  - AC: 사번 중복 시 가입 거부하고 에러를 표시한다.
  - AC: 첫 번째 가입자는 manager로, 이후 가입자는 employee로 자동 등록된다.
  - AC: 비밀번호는 해시되어 저장되고, 가입 완료 후 로그인 화면으로 이동한다.
- 직원으로서, 로그인 후 출근 버튼을 눌러 체크인 시각을 기록하고, 퇴근 시 체크아웃 시각을 기록하고 싶다.
  - AC: 당일 이미 체크인한 경우 버튼이 비활성화되거나 재클릭 시 에러를 표시한다.
  - AC: 체크인 기록이 없으면 체크아웃 버튼이 비활성화된다.
  - AC: 체크아웃은 여러 번 클릭할 수 있으며, 최종 클릭 시각이 체크아웃 시각으로 저장된다.
  - AC: 체크인/체크아웃 시각이 서버 기준 시간으로 저장된다.
- 직원으로서, 시작일/종료일/사유를 입력해 연차를 신청하고 싶다.
  - AC: 시작일이 종료일보다 늦으면 제출이 거부된다.
  - AC: 제출 후 상태는 "대기중"으로 표시된다.
- 직원으로서, 반나절(오전/오후)만 연차를 쓰고 싶을 때 0.5일 단위로 신청하고 싶다.
  - AC: 구분(종일/오전/오후) 드롭다운의 기본값은 "종일"이다.
  - AC: 오전 또는 오후를 선택하면 시작일과 종료일이 같은 날로 고정되고 신청 일수는 0.5일이 된다.
- 관리자로서, 대기 중인 연차 신청 목록을 보고 승인 또는 반려하고 싶다.
  - AC: 목록에는 신청자, 기간, 사유가 표시된다.
  - AC: 처리 후 처리자/처리 시각/결과가 기록되고 목록에서 "대기중" 상태가 사라진다.
  - AC: 이미 처리된 건은 재처리가 불가능하다.
  - AC: manager 본인이 신청한 연차는 본인이 승인/반려할 수 없다(다른 manager만 가능).
- 직원으로서, 내 월별 출퇴근 기록과 연차 사용 내역을 조회하고 싶다.
  - AC: 월 선택 시 해당 월의 체크인/체크아웃 기록과 연차 사용 내역이 표시된다.
  - AC: 본인 데이터만 조회 가능하다.
- 관리자로서, 전체 직원의 월별 출퇴근 기록과 연차 사용 내역을 조회하고 싶다.
  - AC: 월과 직원(전체 또는 개별)을 선택해 조회할 수 있다.
- 가입된 사용자로서, 내 정보 조회 화면에서 비밀번호를 변경하고 싶다.
  - AC: 현재 비밀번호 확인 후에만 변경이 가능하다.
  - AC: 변경 완료 후 재로그인 또는 토큰 재발급이 이루어진다.
- manager로서, 새로운 manager 계정을 직접 생성하고 싶다.
  - AC: 사용자 관리 화면(또는 별도 API)에서 email/이름/사번/입사일/비밀번호를 입력해 manager 역할 계정을 생성할 수 있다.
  - AC: manager만 이 기능에 접근 가능하며, employee는 접근 시 403 응답을 받는다.
  - AC: 생성된 계정은 사번 중복 검사를 동일하게 거친다.
- manager로서, 전사 공통 연차일수를 설정해 전체 직원에게 일괄 적용하고 싶다.
  - AC: 사용자 관리 화면에서 공통 기본 연차일수를 조회/저장할 수 있다.
  - AC: 저장 즉시 전체 직원의 총 연차일수(공통 기본 연차일수 + 입사연도 기준 가산분)가 재계산되어 반영된다(사용일수는 유지).
  - AC: employee는 이 기능에 접근할 수 없다.
- 로그인된 사용자로서, 로그아웃하고 싶다.
  - AC: 로그아웃 시 클라이언트에 저장된 Access Token, Refresh Token을 즉시 삭제한다.
  - AC: 서버 측 Refresh Token 무효화(블랙리스트 처리)는 1차 버전 범위에 포함하지 않는다(5.2 참고).

## 5. 요구사항

### 5.1 기능 요구사항

**인증/사용자 관리**

- 회원가입 시 email, 이름, 사번(고유 식별자), 입사일, 비밀번호를 입력받는다.
- 최초 회원가입자는 자동으로 manager 역할이 부여된다.
- 이후 회원가입자는 기본적으로 employee 역할로 가입된다.
- manager 계정은 회원가입 화면을 통해 생성할 수 없으며, 기존 manager가 직접 생성해야 한다.
- 로그인 시 JWT 기반 Access Token(유효기간 12시간)과 Refresh Token(유효기간 7일)을 발급한다.
- Access Token 만료 시 Refresh Token으로 재발급받을 수 있다.
- 로그인하지 않은 사용자는 근태 관련 기능에 접근할 수 없다.
- 사용자 정보 조회 화면에서 본인 비밀번호를 변경할 수 있다.
- 비밀번호를 입력받는 모든 화면(회원가입/관리자 계정 생성/비밀번호 변경)은 "비밀번호 확인" 입력을 함께 받아 일치 여부를 클라이언트에서 검증한다(서버 API 스펙에는 포함하지 않음).
- manager/employee 역할에 따라 접근 가능한 API와 화면을 제어한다(RBAC).

**출퇴근 관리**

- employee와 manager 모두 로그인 후 출근 체크인, 퇴근 체크아웃을 각각 기록할 수 있다.
- 체크인은 하루 1회를 원칙으로 하며, 이미 체크인한 경우 중복 기록을 막는다.
- 체크아웃은 여러 번 기록할 수 있으며, 그때마다 최종 클릭 시각으로 체크아웃 시각을 덮어쓴다.
- 대시보드에서 이번 달 본인 출근일수와 잔여 연차일수를 요약해 보여준다.

**연차 관리**

- employee와 manager 모두 시작일, 종료일, 사유를 입력해 연차를 신청할 수 있다.
- 연차는 종일(1일) 또는 반차(오전/오후, 0.5일) 단위로 신청할 수 있다. 구분 기본값은 "종일"이며, 반차 선택 시 시작일과 종료일은 같은 날이어야 한다.
- manager는 신청된 연차를 승인 또는 반려할 수 있다(단, 본인이 신청한 건은 제외).
- 연차의 승인/반려 처리자와 처리 시각, 처리 결과가 기록되어야 한다.
- manager 본인이 신청한 연차는 다른 manager가 승인/반려할 수 있다.
- 연차 발생 규칙: manager가 설정하는 전사 공통 연차일수(공통 기본 연차일수)와 입사연도를 근거로 자동 계산한다.
  - 해당연도(올해) 입사자: 0일(공통 연차 미적용)
  - 전년도 입사자: 공통 기본 연차일수 그대로
  - 그 이전 입사자: 공통 기본 연차일수 + (지난 햇수 − 1)
  - 이 계산은 회원가입/manager 계정 생성 시 최초 1회 수행되며, manager가 공통 기본 연차일수를 변경하면 전체 사용자의 총 연차일수가 즉시 재계산되어 반영된다(사용일수는 그대로 유지).
- manager는 사용자 관리 화면에서 전사 공통 기본 연차일수를 조회/변경할 수 있다(개별 직원 단위로 총 연차일수를 직접 수정하는 기능은 제공하지 않는다).
- 잔여 연차일수를 초과하는 신청은 제출 시점에 차단한다(신청 가능일수 부족 시 400 응답).

**근태 현황 조회**

- employee는 본인의 월별 출퇴근 기록과 연차 사용 내역을 조회할 수 있다.
- manager는 전체 직원의 월별 출퇴근 기록과 연차 사용 내역을 조회할 수 있다.

### 5.2 비기능 요구사항

- 백엔드/프론트엔드/데이터베이스 3-tier 아키텍처로 구성한다.
- 데이터베이스는 Supabase의 PostgreSQL 기능만 사용한다(Supabase Auth 등 부가 기능은 사용하지 않는다).
- 백엔드는 Node.js + Express + JavaScript로 개발하며, SOLID 원칙과 Clean 아키텍처를 준수한다.
- 프론트엔드는 최신 버전의 React로 개발하며, 서버 통신에 Tanstack Query, 전역 상태 관리에 별도 라이브러리(Zustand 등)를 사용한다.
- 인증은 자체 구현하며, JWT 기반 Access/Refresh Token 방식을 사용한다(Access 12시간, Refresh 7일).
- 비밀번호는 안전하게 해시하여 저장한다(평문 저장 금지).
- 역할 기반 접근 제어(RBAC)를 백엔드 API 레벨에서 강제한다.
- 동시 접속자 20명 이하 기준으로 설계하며, 별도의 부하 대응 인프라(로드밸런서, 캐시 등)는 두지 않는다.
- 최소 데이터 엔티티: User(사용자), Attendance(출퇴근 기록), LeaveRequest(연차 신청/승인 이력), LeaveBalance(연차 잔여일수), LeavePolicy(전사 공통 연차 정책, 단일 행). 상세 스키마는 별도 설계 문서(4-erd.md)에서 정의한다.
- 모든 시각(체크인/체크아웃, 연차 처리 시각 등)은 Asia/Seoul(KST) 기준으로 저장/표시한다.
- 로그아웃은 클라이언트에서 토큰 삭제로만 처리하며, 서버 측 Refresh Token 무효화(블랙리스트)는 1차 버전 범위에 포함하지 않는다.

### 5.3 우선 순위 기준

- P0(필수): 회원가입/로그인/인증, 출퇴근 체크인·체크아웃, 연차 신청/승인/반려, 월별 현황 조회.
- P1(중요): 비밀번호 변경.
- P2(향후 검토): 관리자에 의한 사용자 정보 수정, 연차 신청 취소/수정 기능, 관리자에 의한 근태 기록 수동 보정, 비밀번호 관리자 재설정.

## 6. 사용자 흐름

**회원가입 및 로그인**

1. 사용자가 회원가입 화면에서 email/이름/사번/입사일/비밀번호를 입력한다.
2. 시스템이 사번 중복 여부를 확인한다. 최초 가입자는 manager, 이후는 employee로 등록된다.
3. 사용자가 로그인하면 Access Token, Refresh Token을 발급받는다.

**출퇴근 기록**

1. employee가 로그인 후 대시보드에서 "출근" 버튼을 클릭한다.
2. 시스템이 당일 체크인 여부를 확인 후 체크인 시각을 기록한다.
3. 퇴근 시 "퇴근" 버튼을 클릭하면 체크아웃 시각을 기록한다(체크인 기록이 없으면 체크아웃 불가). 퇴근 버튼은 여러 번 클릭할 수 있으며, 클릭할 때마다 체크아웃 시각이 최종 클릭 시각으로 갱신된다.

**연차 신청 및 승인**

1. employee가 연차 신청 화면에서 시작일/종료일/사유를 입력해 제출한다.
2. manager가 연차 신청 목록에서 대기 중인 건을 확인하고 승인/반려를 선택한다.
3. 시스템이 처리자, 처리 시각, 처리 결과를 기록하고 신청자에게 결과를 반영한다.

**관리자 계정 생성**

1. manager가 사용자 관리 화면에서 신규 manager 계정 정보(email/이름/사번/입사일/비밀번호)를 입력한다.
2. 시스템이 사번 중복을 확인하고, 통과 시 manager 역할로 계정을 생성한다.
3. employee 역할 사용자가 이 화면/API에 접근하면 403으로 차단된다.

**월별 현황 조회**

1. employee가 월별 현황 화면에서 조회 월을 선택하면 본인의 출퇴근/연차 내역이 표시된다.
2. manager가 월별 현황 화면에서 조회 월과 대상을 선택하면 전체 직원의 출퇴근/연차 내역이 표시된다.

## 7. 범위

### 7.1 In Scope

- 회원가입/로그인/JWT 인증/RBAC
- 사번 기반 사용자 식별, 비밀번호 변경
- 출근/퇴근 체크인/체크아웃 기록
- 연차 신청, 승인/반려 및 처리 이력 관리
- 월별 근태 현황 조회(본인/전체)

### 7.2 Out of Scope

- 급여 계산 및 정산 연동
- 근무 스케줄/교대 관리
- 생체 인식/GPS 기반 출퇴근 인증
- 모바일 네이티브 앱
- 다국어 지원
- 알림(이메일/푸시) 기능

## 8. 엣지 케이스, 예외 처리할 것

케이스별로 처리 방침을 명시한다.

| 케이스                                                    | 처리 방침                                                                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 동일 사번으로 중복 회원가입 시도                          | 사번은 DB 유니크 제약으로 강제. 가입 API는 409 응답과 "이미 등록된 사번입니다" 에러 반환                                                         |
| 당일 이미 체크인한 상태에서 재차 체크인 시도              | 체크인 API는 당일 기록 존재 여부를 먼저 확인, 존재 시 409 응답. 프론트는 체크인 완료 시 버튼을 "체크인 완료"로 비활성화                          |
| 체크인 기록 없이 체크아웃 시도                            | 체크아웃 API는 사용자의 가장 최근 근무 기록을 확인하되, 그 기록이 오늘 또는 어제(KST) 날짜가 아니면(기록 자체가 없는 경우 포함) 체크인 기록 없음으로 간주해 400 응답. 프론트는 당일 체크인 전 체크아웃 버튼을 비활성화       |
| 자정을 넘겨 근무하는 경우                                 | 체크인 시각 기준으로 근무일(work_date)을 결정한다. 체크아웃이 다음날로 넘어가도 같은 work_date에 귀속시킨다                                      |
| 연차 신청 시작일이 종료일보다 늦은 경우                   | 프론트/백엔드 양쪽에서 유효성 검사, 위반 시 400 응답                                                                                             |
| 이미 승인/반려된 연차 신청 재처리 시도                    | 연차 상태(status)가 "대기중"일 때만 승인/반려 API가 동작, 아니면 409 응답                                                                        |
| manager 본인이 신청한 연차를 스스로 승인/반려하려는 경우  | 승인/반려 API에서 처리자 ID와 신청자 ID가 같으면 403 응답으로 차단                                                                               |
| 시스템에 manager가 한 명도 없는 상태                      | 최초 가입자 판별은 "users 테이블에 manager 역할 레코드가 0건인지"로 검사(트랜잭션 내 처리)하여 동시 가입 시에도 최초 1명만 manager가 되도록 보장 |
| Access Token 만료 후 Refresh Token도 만료된 경우          | 프론트에서 401 응답 수신 시 로그인 화면으로 강제 이동, Refresh Token도 만료 시 재로그인 요구                                                     |
| 퇴사 처리된 사용자의 로그인 및 기능 접근 시도             | (범위 확정 필요) 최소 요건으로 사용자 상태(active/inactive) 필드를 두고, 로그인 시 inactive면 403 응답. 퇴사 처리 기능 자체는 P2로 별도 검토     |
| 연차 신청 기간이 이미 승인된 다른 연차 기간과 겹치는 경우 | (범위 확정 필요) 1차 버전은 중복 검사 없이 허용, 필요 시 P1로 추가 검토                                                                          |
| 체크인 후 체크아웃 없이 하루가 종료된 경우                | 1차 버전은 별도 자동 마감 처리 없이 미완료 상태로 남긴다(체크아웃 시각 null). 관리자에 의한 수동 보정 기능은 P2로 향후 검토                      |
| 체크아웃 버튼을 여러 번 클릭하는 경우                      | 에러가 아닌 정상 흐름으로 처리한다. 클릭할 때마다 같은 근무일 레코드의 체크아웃 시각을 최종 클릭 시각으로 덮어쓴다(새 레코드 생성 없음)          |
| 반차(오전/오후)인데 시작일과 종료일이 다른 경우            | 연차 신청 API가 400 응답으로 거부한다(반차는 하루짜리 신청에서만 가능)                                                                           |
