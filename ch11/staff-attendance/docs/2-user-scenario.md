- 로그인하지 않은 상태에서 대시보드 등 근태 관련 화면에 직접 접근하면 로그인 화면으로 리다이렉트된다.

## 시나리오 2. 출퇴근 체크인/체크아웃 (정상 및 중복 시도)

### 등장인물

김사원(employee)

### 사전조건

- 김사원은 로그인된 상태이며 오늘 아직 체크인하지 않았다.

### 단계별 시나리오 (정상 흐름)

1. 김사원은 오전 8시 55분에 대시보드에 접속해 "출근" 버튼을 클릭한다.
2. 시스템은 오늘 날짜(work_date) 기준으로 김사원의 체크인 기록이 없음을 확인하고, 서버 시각(KST) 08:55:12를 체크인 시각으로 저장한다.
3. "출근" 버튼은 "체크인 완료(08:55)"로 바뀌며 비활성화되고, "퇴근" 버튼이 활성화된다.
4. 오후 6시 3분, 김사원은 퇴근 전 "퇴근" 버튼을 클릭한다.
5. 시스템은 당일 체크인 기록이 존재함을 확인하고, 서버 시각 18:03:47을 체크아웃 시각으로 저장한다.
6. "퇴근" 버튼은 계속 활성화 상태로 남아 있고, 화면에는 체크아웃 시각 18:03이 표시된다.
7. 김사원이 자리 정리를 마치고 오후 6시 10분에 "퇴근" 버튼을 한 번 더 클릭한다.
8. 시스템은 같은 근무일 기록의 체크아웃 시각을 18:10:02로 덮어쓴다.

### 기대 결과

- 해당 근무일에 체크인 시각 08:55:12가 저장되고, 체크아웃 시각은 마지막으로 클릭한 18:10:02로 저장된다(KST 기준).
- 하루에 체크인은 1건만 기록되지만, 체크아웃은 버튼을 누를 때마다 같은 근무일 기록에 최종 클릭 시각으로 덮어써진다(별도 레코드가 추가되지 않음).

### 예외 상황 A: 이미 체크인한 상태에서 재차 체크인 시도

1. 김사원이 체크인을 완료한 뒤 실수로(또는 새로고침 오류로) 다시 "출근" 버튼을 눌러본다.
2. 프론트엔드는 이미 "체크인 완료" 상태이므로 버튼이 비활성화되어 있어 클릭 자체가 불가능하다.
3. 만약 API가 직접 재호출되더라도 서버는 당일 체크인 기록 존재를 확인해 409 응답을 반환하고 "이미 체크인하셨습니다" 에러를 표시한다.

### 예외 상황 B: 체크인 없이 체크아웃 시도

1. 김사원이 당일 체크인을 하지 않은 상태에서 실수로 URL을 직접 호출하거나 오래된 화면에서 "퇴근" 버튼을 누른다.
2. 프론트엔드는 체크인 기록이 없으므로 "퇴근" 버튼을 비활성화해 두었기 때문에 정상적으로는 클릭할 수 없다.
3. API가 직접 호출된 경우 서버는 사용자의 가장 최근 근무 기록을 확인한다. 그 기록의 근무일(work_date)이 오늘 또는 어제(KST)가 아니면 — 기록 자체가 없는 경우를 포함해 — 체크인 기록이 없는 것으로 간주해 400 응답과 "체크인 기록이 없습니다" 에러를 반환한다. 오래전 근무일 기록이 실수로 갱신되는 일은 없다.

### 예외 상황 C: 자정을 넘겨 근무하는 경우

1. 김사원이 오후 11시 30분에 체크인한다. 시스템은 체크인 시각 기준으로 근무일을 오늘 날짜로 확정해 저장한다.
2. 다음날 새벽 1시에 김사원이 체크아웃하면, 체크아웃 시각은 다음날이지만 근무일(work_date)은 체크인일 그대로 귀속되어 같은 근태 기록에 저장된다.

## 시나리오 3. 연차 신청

### 등장인물

김사원(employee)

### 사전조건

- 김사원은 로그인된 상태이며 잔여 연차일수가 5일 남아 있다.

### 단계별 시나리오

1. 김사원은 다음 달 가족 여행을 위해 "연차 신청" 화면으로 이동한다.
2. 시작일(2026-09-07), 종료일(2026-09-08), 사유("가족 여행")를 입력한다. 구분 드롭다운은 기본값인 "종일"로 둔 채 "신청" 버튼을 클릭한다.
3. 시스템은 시작일이 종료일보다 늦지 않음을 확인하고, 신청 일수(2일)가 잔여 연차일수(5일) 이내임을 확인한다.
4. 연차 신청이 생성되고 상태는 "대기중"으로 표시된다.
5. 김사원은 "내 연차 신청 내역"에서 방금 제출한 건이 "대기중"으로 조회됨을 확인한다.

### 기대 결과

- 연차 신청 레코드가 생성되며 신청자, 기간, 구분(종일/오전/오후), 사유, 상태("대기중")가 저장된다.
- 잔여 연차일수는 승인 시점에 차감되며(시나리오 4 참고), 신청 시점에는 현재 잔여일수를 초과하는 신청 자체가 차단된다.

### 추가 흐름: 반차(오전/오후) 신청

1. 김사원은 병원 진료를 위해 오전만 연차를 쓰고 싶어 "연차 신청" 화면에서 시작일(2026-09-10)을 입력한다.
2. 구분 드롭다운에서 "오전"을 선택한다. 화면은 종료일을 시작일과 같은 날짜로 자동 맞추고 종료일 입력을 비활성화하며, 신청 일수를 0.5일로 표시한다.
3. 사유("병원 진료")를 입력하고 "신청" 버튼을 클릭한다.
4. 시스템은 신청 일수 0.5일이 잔여 연차일수 이내임을 확인하고 연차 신청을 "대기중" 상태로 생성한다.
5. "내 연차 신청 내역"에는 구분이 "오전 반차"로 표시된다.

### 예외 상황 A: 시작일이 종료일보다 늦은 경우

1. 김사원이 실수로 시작일을 2026-09-10, 종료일을 2026-09-08로 입력하고 제출한다.
2. 프론트엔드에서 즉시 유효성 오류가 표시되며, 혹시 그대로 제출되더라도 서버가 400 응답으로 거부한다.

### 예외 상황 B: 잔여 연차일수를 초과하는 신청

1. 잔여 연차일수가 1일뿐인 김사원이 3일짜리 연차(2026-09-07~09-09)를 신청한다.
2. 시스템은 신청 일수(3일)가 잔여 일수(1일)를 초과함을 확인하고 400 응답과 "잔여 연차일수가 부족합니다" 에러를 반환한다.
3. 신청은 생성되지 않는다.

## 시나리오 4. 연차 승인/반려 (본인 신청 승인 불가 케이스 포함)

### 등장인물

김사원(employee, 신청자), 박팀장(manager, 승인자), 이팀장(manager, 두 번째 승인자)

### 사전조건

- 김사원이 제출한 연차 신청(2026-09-07~09-08, "대기중")이 존재한다.
- 박팀장도 본인 명의로 연차 신청(2026-09-14, "대기중")을 제출해 둔 상태다.

### 단계별 시나리오 (일반 직원 신청 승인)

1. 박팀장은 "연차 승인 관리" 화면에서 "대기중" 상태인 신청 목록을 확인한다. 목록에는 신청자(김사원), 기간(09-07~09-08), 사유("가족 여행")가 표시된다.
2. 박팀장은 김사원의 신청 건을 선택해 내용을 확인하고 "승인" 버튼을 클릭한다.
3. 시스템은 처리자(박팀장), 처리 시각, 처리 결과("승인")를 기록하고, 해당 건의 상태를 "승인됨"으로 변경한다.
4. 목록에서 해당 건은 "대기중" 목록에서 사라지고, 김사원의 잔여 연차일수에서 2일이 차감된다.
5. 김사원은 "내 연차 신청 내역"에서 상태가 "승인됨"으로 바뀐 것을 확인한다.

### 예외 상황 A: 이미 처리된 건 재처리 시도

1. 박팀장이 승인 처리 후, 실수로 새로고침이 안 된 화면에서 같은 건의 "반려" 버튼을 다시 클릭한다.
2. 시스템은 해당 신청의 상태가 이미 "대기중"이 아님을 확인해 409 응답과 "이미 처리된 신청입니다" 에러를 반환한다.
3. 상태는 "승인됨"으로 유지된다.

### 예외 상황 B: manager 본인이 신청한 연차를 스스로 승인/반려하려는 경우

1. 박팀장은 본인이 제출한 연차 신청(09-14)을 "연차 승인 관리" 목록에서 확인한다.
2. 박팀장이 본인 건의 "승인" 버튼을 클릭한다.
3. 시스템은 처리자 ID(박팀장)와 신청자 ID(박팀장)가 동일함을 확인해 403 응답과 "본인이 신청한 연차는 본인이 처리할 수 없습니다" 에러를 반환한다. 목록에서 해당 버튼은 애초에 비활성화되어 있거나, 클릭 시 이 에러 메시지가 노출된다.
4. 다른 manager인 이팀장이 로그인해 같은 목록에서 박팀장의 신청 건을 확인하고 "승인" 버튼을 클릭한다.
5. 시스템은 처리자(이팀장)와 신청자(박팀장)가 다르므로 정상 처리하며, 상태를 "승인됨"으로 변경하고 처리자/처리 시각을 기록한다.

### 기대 결과

- 모든 연차 신청은 승인/반려 시 처리자, 처리 시각, 처리 결과가 남는다.
- manager는 타인이 제출한 연차만 승인/반려할 수 있으며, 본인 신청 건은 다른 manager를 통해서만 처리된다.
- 이미 처리된 신청은 재처리가 불가능하다.

### 기대 결과

- 월 선택 시 해당 월의 본인 출퇴근/연차 데이터만 조회된다.
- 체크아웃이 누락된 날은 별도로 구분되어 표시된다(1차 버전은 자동 보정 없이 미완료 상태로 남김).

## 시나리오 7. 관리자(manager) 계정 생성

### 등장인물

박팀장(manager), 김사원(employee, 접근 차단 케이스에 등장)

### 사전조건

- 회사에 신규 파트장으로 이팀장이 입사 예정이며 manager 권한이 필요하다.
- 박팀장은 로그인된 상태다.

### 단계별 시나리오

1. 박팀장은 "사용자 관리" 화면에서 "관리자 계정 생성" 메뉴로 이동한다.
2. 이메일(`lee.paljang@company.com`), 이름(이팀장), 사번(`MGR2026-002`), 입사일(2026-09-01), 초기 비밀번호를 입력하고 "생성" 버튼을 클릭한다.
3. 시스템은 사번 `MGR2026-002`가 중복되지 않음을 확인한 뒤, manager 역할로 계정을 생성한다.
4. 박팀장에게 생성 완료 메시지가 표시되고, 사용자 목록에 이팀장(manager)이 추가된 것을 확인한다.
5. 이팀장은 전달받은 이메일/초기 비밀번호로 로그인해 manager 권한 화면(연차 승인 관리, 전체 근태 현황 등)에 접근할 수 있음을 확인한다.

### 기대 결과

- 신규 manager 계정이 정상적으로 생성되고, 사번 중복 검사는 일반 회원가입과 동일하게 적용된다.
- 생성 직후부터 manager 전용 기능(연차 승인, 전체 현황 조회, 관리자 계정 생성)에 접근 가능하다.

### 예외 상황: employee가 관리자 계정 생성 기능에 접근 시도

1. 김사원이 우연히 "사용자 관리" 화면 URL을 알게 되어 직접 접근을 시도한다.
2. 시스템은 김사원의 역할이 employee임을 확인하고 403 응답을 반환하며, 화면에는 "접근 권한이 없습니다" 메시지가 표시된다.
3. 김사원은 계정 생성 화면에 진입하지 못한다.

### 추가 흐름: 공통 연차일수 설정

1. 박팀장은 "사용자 관리" 화면 상단의 "공통 연차일수 설정" 카드에서 현재 공통 기본 연차일수(0일)를 확인한다.
2. 박팀장이 값을 15로 입력하고 "저장" 버튼을 클릭한다.
3. 시스템은 값을 저장하고, 전체 직원의 총 연차일수를 입사연도 기준으로 즉시 재계산한다: 올해 입사자는 0일, 작년 입사자는 15일, 그 이전 입사자는 15+(지난 햇수-1)일. 이미 사용한 연차일수(used_days)는 그대로 유지된다.
4. 사용자 목록 테이블의 "총 연차일수"/"사용·잔여 연차" 컬럼이 갱신된 값으로 즉시 반영된다.
5. 김사원(employee)이 이 API를 직접 호출하면 403으로 차단된다.

## 시나리오 8. 비밀번호 변경

김사원(employee)

## 시나리오 9. 로그아웃

### 등장인물

김사원(employee)

### 사전조건

- 김사원은 로그인된 상태이며 Access Token, Refresh Token을 보유하고 있다.

### 단계별 시나리오

1. 김사원은 화면 상단의 "로그아웃" 버튼을 클릭한다.
2. 클라이언트는 저장하고 있던 Access Token과 Refresh Token을 즉시 삭제한다.
3. 김사원은 로그인 화면으로 이동한다.
4. 김사원이 브라우저 뒤로가기 등으로 대시보드에 재접근을 시도하면, 토큰이 없으므로 로그인 화면으로 다시 리다이렉트된다.

### 기대 결과

- 로그아웃 시 클라이언트에 저장된 토큰이 즉시 삭제된다.
- 서버 측 Refresh Token 무효화(블랙리스트 처리)는 이루어지지 않는다(1차 버전 범위 밖).
