## 제품 아이디어

- 제품명: [제품명]
- 배경: [지금 이 문제가 왜 존재하는가 - 현재 방식의 어떤 점이 불편하거나 비효율적인가]
- 타겟 사용자: [누가 쓰는가 - 규모, 업종, 역할 등 구체적으로]
- 페르소나:
  - [역할1](예: 김사원): [이 사람이 이 제품으로 하고 싶은 것]
  - [역할2](예: 박팀장): [이 사람이 이 제품으로 하고 싶은 것]

## 핵심 기능(우선순위 표시: [기능마다 P0/P1/P2 중 하나])

1. [기능 영역 1 이름, 예: 인증/사용자 관리]
   - [세부 동작 1: 누가 무엇을 할 수 있는가, 어떤 조건/제약이 있는가]
   - [세부 동작 2]
   - [세부 동작 3 - 있다면]
2. [기능 영역 2 이름]
   - [세부 동작 1]
   - [세부 동작 2]
3. [기능 영역 3 이름]
   - [세부 동작 1]
   - [세부 동작 2]
4. [기능 영역 4 이름 - 필요한 만큼 추가]

## 비기능 요구사항

- [아키텍처 구성: 예 - 3-tier, 모놀리식, 서버리스 등]
- [데이터베이스: 어떤 DB를 쓰는가, 어떤 부가 기능은 쓰지 않는가]
- [백엔드 기술 스택 및 개발 원칙: 예 - 언어/프레임워크, 아키텍처 원칙]
- [프론트엔드 기술 스택: 예 - 프레임워크, 상태관리/서버통신 라이브러리]
- [인증 방식: 자체구현/외부연동 여부, 토큰 방식과 유효기간 등]
- [보안 요구사항: 비밀번호 저장 방식, 접근 제어 방식 등]
- [성능/규모 가정: 동시 사용자 수, 부하 대응 인프라 필요 여부]
- [시간대/지역화 기준: 예 - 특정 타임존 고정 여부]
- [최소 데이터 엔티티 목록: 이 제품에 꼭 필요한 핵심 테이블/모델 이름을 나열]

## 비목표(이번 버전에서 하지 않을 것)

- [명시적으로 범위에서 뺄 기능 1]
- [명시적으로 범위에서 뺄 기능 2]
- [향후(P2)로만 남겨둘 기능들이 있다면 별도로 명시]

## 진행 방식

1. 위 내용만으로 PRD를 쓰기에 애매하거나 결정이 안 된 부분(예: 엣지 케이스 처리 방침, 성공 지표 수치, 작업 일정 등)이 있으면 먼저 나에게 질문해라. 임의로 추측해서 채우지 마라.
2. 답변을 받은 뒤에만 아래 목차대로 PRD를 작성해라.
3. 한국어, Markdown으로 작성한다.

## PRD 목차 (아래 순서와 번호를 그대로 따를 것)

1. 개요 (1.1 배경 / 1.2 목표 / 1.3 비목표)
2. 문제 정의 (2.1 사용자 문제)
3. 목표 및 성공 지표 (3.1 핵심목표 / 3.2 성공 지표 / 3.3 실패 조건)
4. 사용자 시나리오 (4.1 페르소나 / 4.2 사용자 스토리 — 스토리마다 완료 조건(Acceptance Criteria) 포함)
5. 요구사항 (5.1 기능 요구사항 / 5.2 비기능 요구사항 / 5.3 우선순위 기준: P0/P1/P2)
6. 사용자 흐름 (핵심 플로우별로 단계 서술)
7. 범위 (7.1 In Scope / 7.2 Out of Scope)
8. 엣지 케이스, 예외 처리할 것 (표: 케이스 | 처리 방침 — 위 핵심 기능들의 중복 입력, 순서 역전, 권한 없는 접근, 동시성 충돌, 만료/재처리 시도 등 있을 법한 예외 상황을 빠짐없이 포함)
9. 작업 일정 (단계별 대략적인 기간)

## 작성 시 지켜야 할 것

- 모호한 표현("적절히", "필요시", "나중에") 대신 구체적인 기준·숫자·조건으로 서술한다.
- 각 기능 요구사항과 사용자 스토리는 "누가/무엇을/어떤 조건에서"가 드러나게 쓰고, 예외 상황까지 함께 고려한다.
- 이 PRD를 근거로 이후 사용자 시나리오·와이어프레임·ERD·실행계획 문서를 순서대로 만들 것이므로, 뒤 문서에서 참조하기 쉽게 섹션 번호와 제목을 명확히 단다.
- 문서 맨 위에 변경 이력 표(버전/날짜/변경 내용/작성자)를 포함한다.
- 결과물은 `docs/1-prd.md`에 저장한다.
