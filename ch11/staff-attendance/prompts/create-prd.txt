너는 시니어 프로덕트 매니저다. 아래 제품 아이디어를 바탕으로 PRD(제품 요구사항 정의서)를 작성해줘.

## 제품 아이디어

- 제품명: 소규모 사업장 근태관리 앱
- 배경: 임직원 20명 내외의 소규모 중소기업은 별도 근태관리 시스템 없이 수기 또는 엑셀로 출퇴근과 연차를 관리하는 경우가 많다. 이 때문에 기록 누락, 연차 승인 이력 관리 부재, 월별 현황 집계의 어려움이 발생한다.
- 타겟 사용자: 임직원 20명 내외 소규모 사업장의 일반 직원과 관리자
- 페르소나:
  - 일반 직원(김사원): 매일 출퇴근 시각을 기록하고, 필요 시 연차를 신청하며, 본인 근태 현황을 확인하고 싶어 한다.
  - 관리자(박팀장): 직원들의 연차 신청을 검토해 승인/반려하고, 전체 직원의 월별 근태 현황을 파악해 인사 관리에 활용하고 싶어 한다.

## 핵심 기능(전부 필수 P0, 비밀번호 변경만 P1)

1. 인증/사용자 관리
   - 회원가입 시 email/이름/사번(고유 식별자)/입사일/비밀번호를 입력받는다.
   - 최초 가입자는 자동으로 manager 역할, 이후 가입자는 employee 역할이 된다. manager 계정은 회원가입 화면으로 만들 수 없고 기존 manager가 직접 생성해야 한다.
   - JWT 기반 Access Token(12시간)/Refresh Token(7일) 발급, Access Token 만료 시 Refresh Token으로 재발급.
   - 로그인하지 않은 사용자는 근태 기능에 접근 불가. manager/employee 역할별 접근 제어(RBAC)를 API 레벨에서 강제.
   - 본인 비밀번호 변경 가능(현재 비밀번호 확인 필요, 변경 후 재로그인 또는 토큰 재발급).
   - manager는 새로운 manager 계정을 직접 생성할 수 있다(employee는 403).
   - 로그아웃은 클라이언트 토큰 삭제로만 처리(서버 측 블랙리스트는 범위 밖).
2. 출퇴근 관리
   - employee/manager 모두 출근 체크인, 퇴근 체크아웃 기록 가능.
   - 체크인은 하루 1회만 허용(중복 시도 차단). 체크아웃은 여러 번 기록 가능하며, 매번 최종 클릭 시각으로 덮어쓴다.
   - 자정을 넘겨 근무해도 근무일(work_date)은 체크인 시각 기준으로 고정된다.
   - 대시보드에 이번 달 본인 출근일수와 잔여 연차일수를 요약 표시.
3. 연차 관리
   - employee/manager 모두 시작일/종료일/사유를 입력해 연차 신청 가능. 종일(1일) 또는 반차(오전/오후, 0.5일) 단위 지원. 반차는 시작일=종료일이어야 한다.
   - manager가 신청된 연차를 승인/반려(단, 본인이 신청한 건은 본인이 처리 불가, 다른 manager만 가능). 처리자/처리시각/결과가 기록된다. 이미 처리된 건 재처리 불가.
   - 잔여 연차일수를 초과하는 신청은 제출 시점에 차단(400).
   - 연차 발생 규칙: manager가 설정하는 "전사 공통 기본 연차일수"와 각 직원의 입사연도를 근거로 총 연차일수를 자동 계산한다.
     - 올해(해당연도) 입사자: 0일
     - 작년(전년도) 입사자: 공통 기본 연차일수 그대로
     - 그 이전 입사자: 공통 기본 연차일수 + (지난 햇수 − 1)
     - 이 계산은 가입 시점에 1회 수행되고, manager가 공통 기본 연차일수를 변경하면 전체 직원의 총 연차일수가 즉시 재계산된다(이미 사용한 연차일수는 유지).
   - manager는 사용자 관리 화면에서 이 공통 기본 연차일수를 조회/변경할 수 있다(개별 직원 단위로 직접 수정하는 기능은 없음).
4. 근태 현황 조회
   - employee는 본인의 월별 출퇴근 기록/연차 사용 내역만 조회 가능.
   - manager는 전체 직원(또는 개별 직원 선택)의 월별 출퇴근/연차 내역을 조회 가능.

## 비기능 요구사항

- 백엔드/프론트엔드/데이터베이스 3-tier 아키텍처.
- 데이터베이스는 Supabase의 PostgreSQL 기능만 사용(Supabase Auth 등 부가 기능 사용 안 함).
- 백엔드: Node.js + Express + JavaScript, SOLID 원칙과 Clean 아키텍처 준수.
- 프론트엔드: 최신 버전 React, 서버 통신은 Tanstack Query, 전역 상태 관리는 별도 라이브러리(Zustand 등).
- 인증은 자체 구현(JWT Access/Refresh), 비밀번호는 반드시 해시 저장(평문 금지).
- RBAC는 백엔드 API 레벨에서 강제.
- 동시 접속자 20명 이하 기준으로 설계, 별도 부하 대응 인프라(로드밸런서/캐시 등) 불필요.
- 모든 시각은 Asia/Seoul(KST) 기준으로 저장/표시.
- 최소 데이터 엔티티: User, Attendance, LeaveRequest, LeaveBalance, LeavePolicy(전사 공통 연차 정책, 단일 행).

## 비목표(이번 버전에서 하지 않을 것)

- 급여 계산, 4대 보험, 세무 연동 등 급여/인사 정산
- 근무 스케줄(교대/시프트) 관리
- 생체 인식, GPS 기반 위치 인증
- 모바일 네이티브 앱(웹으로만 제공)
- 다국어(i18n) 지원
- 이메일 발송 기반 비밀번호 재설정(관리자 수동 재설정은 P2 향후 검토)
- 관리자에 의한 사용자 정보 수정, 연차 신청 취소/수정, 관리자에 의한 근태 기록 수동 보정도 P2 향후 검토로만 남긴다

## 진행 방식

1. 위 내용만으로 PRD를 쓰기에 애매하거나 결정이 안 된 부분(예: 엣지 케이스 처리 방침, 성공 지표 수치, 작업 일정 등)이 있으면 먼저 나에게 질문해라. 임의로 추측해서 채우지 마라.
2. 답변을 받은 뒤에만 아래 목차대로 PRD를 작성해라.
3. 한국어, Markdown으로 작성한다.

## PRD 목차 (아래 순서와 번호를 그대로 따를 것)

1. 개요 (1.1 배경 / 1.2 목표 / 1.3 비목표)
2. 문제 정의 (2.1 사용자 문제)
3. 목표 및 성공 지표 (3.1 핵심목표 / 3.2 성공 지표 / 3.3 실패 조건)
4. 사용자 시나리오 (4.1 페르소나 / 4.2 사용자 스토리 — 스토리마다 완료 조건(Acceptance Criteria) 포함)
5. 요구사항 (5.1 기능 요구사항 / 5.2 비기능 요구사항 / 5.3 우선순위 기준: P0/P1/P2)
6. 사용자 흐름 (핵심 플로우별로 단계 서술)
7. 범위 (7.1 In Scope / 7.2 Out of Scope)
8. 엣지 케이스, 예외 처리할 것 (표: 케이스 | 처리 방침 — 체크인/체크아웃 중복, 자정 근무, 연차 날짜 역전, 재처리, 본인 승인 시도, 최초 manager 동시가입, 토큰 만료, 퇴사 계정, 연차 기간 중복, 미완료 근무, 체크아웃 재클릭, 반차 날짜 불일치 등을 반드시 포함)
9. 작업 일정 (단계별 대략적인 기간)

## 작성 시 지켜야 할 것

- 모호한 표현("적절히", "필요시", "나중에") 대신 구체적인 기준·숫자·조건으로 서술한다.
- 각 기능 요구사항과 사용자 스토리는 "누가/무엇을/어떤 조건에서"가 드러나게 쓰고, 예외 상황까지 함께 고려한다.
- 이 PRD를 근거로 이후 사용자 시나리오·와이어프레임·ERD·실행계획 문서를 순서대로 만들 것이므로, 뒤 문서에서 참조하기 쉽게 섹션 번호와 제목을 명확히 단다.
- 문서 맨 위에 변경 이력 표(버전/날짜/변경 내용/작성자)를 포함한다.
- 결과물은 `docs/1-prd.md`에 저장한다.
