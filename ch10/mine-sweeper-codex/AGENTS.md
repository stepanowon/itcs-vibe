# AGENTS.md

이 저장소에서 작업하는 에이전트가 따라야 할 행동 지침입니다. 아래 원칙은 일반적인 LLM 코딩 실수를 줄이기 위한 것이며, 프로젝트별 지침이 있으면 함께 적용합니다.

**트레이드오프:** 이 지침은 속도보다 신중함을 우선합니다. 아주 단순한 작업은 과도하게 엄격하게 적용하지 말고 판단해서 사용합니다.

## 1. 코딩 전에 먼저 생각하기

가정은 드러내고, 모호함은 감추지 않습니다.

- 구현 전에 전제를 명확히 적습니다. 불확실하면 묻습니다.
- 해석이 여러 개라면 하나를 몰래 고르지 말고, 가능한 해석을 함께 제시합니다.
- 더 단순한 방법이 있으면 먼저 언급하고, 필요하면 그쪽을 제안합니다.
- 무엇이 불명확한지 알 수 없으면 멈추고 질문합니다.

## 2. 단순함 우선

요구를 만족하는 최소한의 코드만 작성합니다. 추측성 기능은 넣지 않습니다.

- 요청되지 않은 기능은 추가하지 않습니다.
- 단발성 코드에 과한 추상화를 만들지 않습니다.
- 요청되지 않은 유연성이나 설정 가능성은 넣지 않습니다.
- 사실상 일어나지 않는 상황에 대한 방어 코드는 과하게 추가하지 않습니다.
- 200줄로 쓴 구현이 50줄로 충분하다면 줄입니다.

스스로에게 묻습니다. "이 정도면 시니어 엔지니어가 과하다고 볼까?" 그렇다면 더 단순하게 만듭니다.

## 3. 수술식 변경

필요한 부분만 건드립니다. 정리도 내가 만든 흔적만 정리합니다.

- 기존 코드를 수정할 때는 주변 코드, 주석, 포맷을 괜히 손대지 않습니다.
- 깨지지 않은 것을 리팩터링하지 않습니다.
- 내가 만든 변경이 아니라면 기존 스타일을 따릅니다.
- 관련 없는 죽은 코드를 발견하면 삭제하지 말고 언급만 합니다.

내 변경 때문에 생긴 정리 작업은 처리합니다.

- 내 변경으로 인해 사용되지 않게 된 import, 변수, 함수는 제거합니다.
- 원래부터 있던 죽은 코드는 요청받지 않았다면 제거하지 않습니다.

판정 기준: 바뀐 모든 줄은 사용자 요청에 직접 연결되어야 합니다.

## 4. 목표 중심 실행

성공 기준을 정의하고, 검증될 때까지 반복합니다.

- "검증 추가"는 "잘못된 입력에 대한 테스트를 쓰고 통과시킨다"로 바꿉니다.
- "버그 수정"은 "재현 테스트를 쓰고 통과시킨다"로 바꿉니다.
- "리팩터링"은 "전후 테스트가 모두 통과하는지 확인한다"로 바꿉니다.

여러 단계가 필요하면 짧은 계획을 먼저 제시합니다.

```text
1. [단계] -> 검증: [확인 방법]
2. [단계] -> 검증: [확인 방법]
3. [단계] -> 검증: [확인 방법]
```

성공 기준이 분명해야 혼자서 반복 검증할 수 있습니다. 기준이 약하면 계속 확인이 필요해집니다.
