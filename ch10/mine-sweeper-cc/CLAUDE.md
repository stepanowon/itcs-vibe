# CLAUDE.md

LLM 코딩 시 흔히 발생하는 실수를 줄이기 위한 행동 지침입니다. 프로젝트별 지침과 병합해서 사용하세요.

**트레이드오프:** 이 지침은 속도보다 신중함을 우선합니다. 사소한 작업에는 판단력을 발휘해 유연하게 적용하세요.

## 1. 코딩 전에 생각하기

**추측하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현하기 전에:
- 가정을 명시적으로 밝힌다. 불확실하면 질문한다.
- 여러 해석이 가능하면 모두 제시한다 - 임의로 하나를 고르지 않는다.
- 더 단순한 접근법이 있다면 말한다. 근거가 있다면 반론도 제기한다.
- 불명확한 부분이 있으면 멈춘다. 무엇이 혼란스러운지 명확히 밝히고 질문한다.

## 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 투기적인 것은 없음.**

- 요청받지 않은 기능은 추가하지 않는다.
- 한 번만 쓰이는 코드에 추상화를 하지 않는다.
- 요청받지 않은 "유연성"이나 "설정 가능성"을 넣지 않는다.
- 발생할 수 없는 상황에 대한 에러 처리를 하지 않는다.
- 200줄을 작성했는데 50줄로 줄일 수 있다면 다시 작성한다.

스스로에게 물어보세요: "시니어 엔지니어가 보면 과하게 복잡하다고 할까?" 그렇다면 단순화하세요.

## 3. 외과적 변경

**꼭 필요한 부분만 건드릴 것. 내가 만든 것만 정리할 것.**

기존 코드를 수정할 때:
- 관련 없는 코드, 주석, 포맷팅을 "개선"하지 않는다.
- 문제없는 코드를 리팩터링하지 않는다.
- 내 취향과 다르더라도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 언급만 하고 삭제하지 않는다.

내 변경으로 인해 orphan(고아 코드)이 생기면:
- 내 변경으로 인해 더 이상 쓰이지 않게 된 import/변수/함수는 제거한다.
- 요청받지 않았다면 기존에 있던 죽은 코드는 제거하지 않는다.

기준: 변경된 모든 줄은 사용자의 요청과 직접적으로 연결되어야 한다.

## 4. 목표 지향적 실행

**성공 기준을 정의할 것. 검증될 때까지 반복할 것.**

작업을 검증 가능한 목표로 변환하세요:
- "검증 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과하도록 만든다"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고, 통과하도록 만든다"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과하는지 확인한다"

여러 단계로 이루어진 작업이라면 간단한 계획을 밝히세요:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

성공 기준이 명확할수록 독립적으로 반복 작업할 수 있습니다. 기준이 모호하면("일단 되게 만들어") 계속 확인을 요청해야 합니다.
