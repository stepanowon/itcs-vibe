# CSR vs SSR 비교 예제

같은 라우트 구성(홈 `/`, 소개 `/about`, 글 목록 `/posts`)을 CSR(React + Vite)과 SSR(Next.js)로 각각 구현한 두 개의 독립된 프로젝트입니다.
두 프로젝트 모두 글 목록을 가져오는 데 1.2초의 인위적인 지연을 넣어 렌더링 방식의 차이가 눈에 보이도록 했고, 상단 네비게이션에 "클릭 카운트" 버튼을 두어 라우팅 방식의 차이도 확인할 수 있게 했습니다.

- `csr-app/` — React + Vite + React Router. 최초 접속 시 JS 번들을 전부 내려받고, 이후 라우팅/렌더링을 모두 브라우저 안에서 처리합니다.
- `ssr-app/` — Next.js (App Router). 라우트 경로로 직접 요청하면 서버가 그 경로에 맞는 완성된 HTML을 내려주고, 이후 링크 이동은 클라이언트 쪽에서 처리합니다.

## 실행 방법

### CSR (React + Vite)

```bash
cd csr-app
npm install
npm run dev
```

http://localhost:5173 접속

### SSR (Next.js)

```bash
cd ssr-app
npm install
npm run dev
```

http://localhost:3000 접속

## 비교 포인트

### 1. 라우트를 직접 요청했을 때 (view-source / curl)

- **CSR**: 프로덕션 빌드 기준으로 `curl http://localhost:5173/`, `/about`, `/posts` 를 각각 호출해도 **셋 다 완전히 동일한** `<div id="root"></div>` 뿐인 HTML이 옵니다. 서버(Vite)는 경로를 전혀 구분하지 않고 항상 같은 `index.html`을 내려주며, 실제로 어떤 화면을 그릴지는 브라우저에 내려간 JS(React Router)가 URL을 보고 결정합니다.
- **SSR**: `curl http://localhost:3000/`, `/about`, `/posts` 를 각각 호출하면 **경로마다 다른, 이미 내용이 채워진** HTML이 옵니다. 서버가 요청받은 경로에 맞는 페이지를 직접 렌더링해서 보내주기 때문입니다.

### 2. 로딩 경험 (글 목록 페이지)

- **CSR**: `/posts` 접속 시 잠깐 "데이터 로딩 중..." 문구가 보이다가 1.2초 뒤 목록이 나타납니다. (빈 화면 → 로딩 상태 → 콘텐츠)
- **SSR**: `/posts`에 접속하면 응답을 받는 시점에 이미 완성된 콘텐츠가 포함되어 있어 로딩 상태 없이 바로 보입니다. 대신 서버가 응답하기까지 1.2초가 걸립니다. (흰 화면 → 콘텐츠, 중간 로딩 상태 없음)

### 3. 링크 이동 vs 새로고침 — "클릭 카운트"로 확인하기

각 앱 상단 네비게이션에는 "클릭 카운트" 버튼이 있습니다. 이 버튼을 몇 번 누른 뒤:

- **홈 / 소개 / 글 목록 링크를 클릭**해서 이동하면 → 두 앱 모두 카운트가 **유지**됩니다. 페이지 전체를 다시 받아오지 않고, 브라우저 안에서 필요한 부분만 바꿔 그리기 때문입니다(SSR도 최초 로딩 이후에는 이렇게 CSR처럼 동작합니다).
- **주소창에 URL을 직접 입력하거나 새로고침(F5)** 하면 → 두 앱 모두 카운트가 **0으로 초기화**됩니다. 브라우저가 페이지를 완전히 새로 불러오면서 JS 상태가 전부 리셋되기 때문입니다.

즉 SSR 앱도 "최초 진입/새로고침 시에는 서버가 HTML을 만들어 보내고, 그 이후 링크 이동부터는 CSR처럼 동작한다"는 것을 이 카운트로 직접 확인할 수 있습니다.

### 4. 렌더링 시각 표시

각 페이지에 "렌더된 시각"이 표시됩니다.
- CSR은 새로고침해도 이 시각이 **브라우저의 현재 시각**과 같습니다 (클라이언트에서 계산).
- SSR은 새로고침할 때마다 **서버가 응답을 만든 시각**이 찍힙니다 (서버에서 계산, `force-dynamic`으로 캐시 없이 매 요청마다 재실행). 반면 링크로 이동한 경우에는 그 시점에 서버가 다시 렌더링한 시각이 표시되며, 페이지 전체가 새로고침되지는 않습니다.

### 5. SEO / 크롤러 관점

JS를 실행하지 않는 크롤러나 `curl` 같은 도구는 CSR의 모든 경로에서는 빈 화면만, SSR의 각 경로에서는 그 경로에 맞는 완성된 콘텐츠를 봅니다.

### 6. 서버 부하 vs 클라이언트 부하

- CSR: 서버는 어떤 경로든 같은 정적 파일만 주면 되므로 가볍지만, 라우팅/렌더링/데이터 조회 비용이 매 사용자의 브라우저에서 발생합니다.
- SSR: 최초 요청(또는 새로고침)마다 서버가 해당 경로의 데이터를 조회하고 HTML을 만들어야 하므로 서버 부하가 더 크지만, 클라이언트는 완성된 결과를 먼저 받고 이후 이동은 CSR과 같은 가벼운 방식으로 처리됩니다.
